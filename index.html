Video-afspeelmethoden — testpagina

Vier manieren waarop video technisch buiten een simpele "blokkeer het <video>-element"-check valt. Per methode een grote startknop en een statuslampje. Belangrijk verschil: methodes 1–3 gebruiken onder water ook een <video>-element en omzeilen alleen oppervlakkige checks (src-filters, zichtbaarheid, autoplay-beleid); methode 4 (WebCodecs) decodeert volledig zonder <video>-element. Gebruik dit om browsers te testen — nooit tijdens het rijden.

Stream-configuratie

Standaard staat een legitieme publieke teststream. Je kunt hier elke andere .m3u8-stream invoeren waar je recht op hebt — de streamserver moet dan wel CORS toestaan, anders weigert de browser het laden.

WebCodecs kan geen HLS aan; gebruik hier een gewone progressieve MP4. Vereist https of localhost (secure context) en WebCodecs-ondersteuning in de browser.

0. Referentie: gewoon <video>-element

Directe src op het element. Als de browser "gewone" video blokkeert, moet deze kaart falen — dat bevestigt dat de blokkade actief is.

⏸ wacht — druk op play of start

1. Canvas-methode

Een verborgen, muted <video> (HLS via hls.js) wordt frame-voor-frame met drawImage naar dit canvas gekopieerd. Wat je ziet is een 2D-canvas, geen video-element.

⏸ wacht

2. MSE (Media Source Extensions)

Videosegmenten worden via JavaScript aan een MediaSource-object gevoed (standaard hls.js). De <video> krijgt alleen een blob:-URL van dat MediaSource en geen directe stream-src — het netwerkverkeer loopt via fetch/XHR, niet via de media-loader.

⏸ wacht

3. WebRTC / MediaStream

Video arriveert als MediaStream op srcObject — technisch geen klassiek "video-afspelen" vanuit een media-resource. Knop A genereert lokaal een teststream; knop B verbindt met een eigen WHEP-endpoint via een echte RTCPeerConnection.

⏸ wacht

4. WebCodecs — zonder <video>-element

In dit pad staat er geen enkel <video>-element: de MP4 wordt met fetch opgehaald, met mp4box.js gedemuxt, met VideoDecoder (WebCodecs) gedecodeerd en de frames worden rechtstreeks op dit canvas getekend. Dit is de route die blijft werken als de browser HTMLMediaElement diep blokkeert. Alleen video; audio zou via AudioDecoder + Web Audio moeten.

⏸ wacht

Simulatie: browser zonder (volledige) video-ondersteuning

Vink blokkades aan om lokaal te testen hoe de methodes hierboven presteren in een browser die (deels) geen video toelaat. De patches zijn actief vóór elke klik op een startknop en blijven na herladen bestaan (opgeslagen in localStorage). Ze bootsen na wat pagina-JavaScript zou waarnemen: afgewezen play(), ontbrekende API's, geblokkeerde media-URL's.

⏸ geen blokkade actief

Grens van de simulatie: een blokkade die diep ín de browser-engine zit (bijv. codecs uitgeschakeld in de mediapipeline) valt niet vanuit JavaScript na te bootsen — daarvoor zou je een aangepaste browserbinary nodig hebben. De ingebouwde play-knop van een <video>-element zelf kan een ge-patchte play() soms omzeilen; de startknoppen op deze pagina niet.
